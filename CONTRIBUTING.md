# Contributing

Thanks for helping improve this repository. Contributions should make the project clearer, more accurate, or more useful to someone learning GitHub collaboration.

## Before you start

- Read the README and check existing issues and pull requests.
- For a substantial change, open or comment on an issue first. Explain the problem and proposed scope.
- Keep changes focused. One pull request should normally address one related task.
- Do not create activity solely to chase profile achievements.

## Good first contributions

- Fix unclear wording, typos, or broken links.
- Add a concise, reproducible GitHub workflow example.
- Improve issue or pull request templates.
- Document a real limitation, accessibility concern, or lesson learned.
- Verify an existing instruction against current GitHub behavior and cite an authoritative source when useful.

## Branch and pull request workflow

1. Fork the repository if you do not have write access to the upstream repository.
2. Update your local `main` from the upstream repository before starting, so your work is based on a current version.
3. Create a descriptive branch, for example `docs/clarify-pr-workflow`.
4. Make the smallest complete change that solves the issue.
5. Review the diff for accidental changes, spelling, working links, and correct Markdown rendering.
6. Commit with a concise message that describes the change, such as `docs: clarify pull request steps`.
7. Push the branch to your fork and open a pull request against the upstream repository's `main` branch.
8. In the pull request description, include:
   - The problem or motivation.
   - A summary of what changed.
   - The related issue, if any.
   - Checks performed (for example, link and Markdown review).
9. Respond constructively to review feedback. Add follow-up commits rather than force-pushing over shared work unless the maintainers request it.

Do not merge your own pull request unless you have the required permission and the repository's contribution rules allow it. A pull request is a proposal for review, not a guarantee of acceptance.

## Co-authored commits

Use a `Co-authored-by` trailer only when another person made a genuine contribution to that commit and has agreed to be credited.

- Ask the co-author which name and email address they want shown.
- Use an email address associated with their GitHub account, including their GitHub-provided noreply address when appropriate.
- Add one trailer per genuine co-author at the end of the commit message, separated from the message body by a blank line.

Example format (replace the placeholders only with details confirmed by the contributors):

```text
docs: improve the collaboration guide

Clarify the review and contribution steps.

Co-authored-by: Contributor Name <contributor@example.com>
```

Never guess an email address, add someone who did not contribute, or use co-authorship as an achievement shortcut. GitHub's documentation explains the supported trailer format and email requirements: [Creating a commit with multiple authors](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/creating-a-commit-with-multiple-authors).

## Discussions and accepted answers

Use GitHub Discussions for questions and reusable knowledge that benefit the wider community. Search existing discussions first, provide enough context to make a question answerable, and explain why a proposed answer solves the problem.

Only the person or maintainers with the appropriate permissions should mark an answer as accepted, and only when it genuinely resolves the question. Do not create artificial questions, ask for self-awarded answers, or trade accepted answers for profile activity.

## Quality checklist

Before requesting review, confirm:

- [ ] The change addresses a real issue or improves the documentation.
- [ ] The diff contains no unrelated changes.
- [ ] Markdown formatting and links were checked.
- [ ] Any factual GitHub behavior is current and supported by a reliable source.
- [ ] Credits and co-author trailers are accurate and consented to.
- [ ] The pull request explains the motivation, changes, and checks performed.

## Code of conduct for contributions

Be respectful, assume good faith, and focus feedback on the work. Do not spam contributors, fabricate activity, misrepresent authorship, or promise that a contribution will earn a GitHub achievement.
